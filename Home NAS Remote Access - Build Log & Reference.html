The Big Picture

What got built here, in one sentence: files sitting on a physical NAS in your house can now be opened, edited, and saved from any device, on any network, anywhere with an internet connection — exactly as if you were sitting at home on the LAN — without ever opening a single port to the public internet.

The rest of this guide walks through it in order: the problem, the state everything was in before, why the obvious-sounding fixes didn't work, the actual plan, a full step-by-step build log (detours included — several things had to be tried, hit an error, and get diagnosed before landing on the real fix), where things stand now, and how to connect to your personal folder going forward from any device.

The Problem We Set Out To Solve

The starting goal was simple: a Netgear ReadyNAS RN202, freshly set up with two 2TB drives, meant to hold a Plex media library and act as general-purpose storage — the same role as an external hard drive, but shared across every device in the house, with an eventual plan to auto-backup iPhone photos/videos to it too.

Getting it reachable on the home network was the easy part. The real problem was that plain file sharing (SMB) only works on the local network by default — the moment you leave the house, or switch to cellular data, the NAS simply isn't reachable at all. The actual goal was always remote access: open the same folders from a laptop at a coffee shop or a phone on cellular data, with the exact same experience as being home.

Where We Started

Every Device Already Had Tailscale, Except the NAS

One important piece of context turned out to make the whole project much simpler than it first looked: every personal device already had the Tailscale app installed individually — the laptops, the phone, and the Alienware machine's Ubuntu install — used for remotely controlling that Ubuntu box via RustDesk. That meant device-to-device access between those machines already worked from anywhere, no extra setup required.

The NAS was the one thing missing from that picture. It never had Tailscale on it, and — as covered in The Plan below — never realistically could. The Tailscale device list itself was also a little messy at this point: an earlier, half-broken attempt to install Tailscale on the Ubuntu server had left a dead duplicate node (cbm-alienware-ubuntu) sitting alongside the one that actually worked (cbm-alienware-ubuntu-1).

Early Dead Ends Before the Real Fix

Two false starts, worth knowing about since they're easy to repeat:

Common Pitfall

RAIDar needs Java. Netgear's own discovery tool for the ReadyNAS 200-series (RAIDar) requires a separate OpenJDK/Java install just to launch — a heavyweight dependency for finding one IP address. It was abandoned in favor of just checking the router's own connected-devices list, which needed no extra software at all.

Common Pitfall

The DLNA entry isn't the file share. Windows File Explorer auto-discovers the NAS under Network locations — but that entry is the NAS's DLNA media-server advertisement, a completely different thing from its SMB file shares. It even kept showing the NAS's old factory name after the device was renamed, because DLNA's "friendly name" is a separate setting from the system hostname. Double-clicking it only ever surfaced a thin Music/Pictures/Video/Browse-Folders view — never the real clayton-docs/vault shares. The fix was to always map the real UNC path directly (\\cbm-nas-01\sharename or its IP), never to browse in through the auto-discovered device icon.

The Plan

Why the NAS Can't Run Tailscale Itself

ReadyNAS OS 6 (the RN202's operating system) runs on an ARM chip (Annapurna Alpine) with no Docker support and no official Tailscale package in its app store. It's technically possible to enable root SSH access and manually drop an ARM Tailscale binary onto it, but that's an unsupported hack — nothing keeps it running or updated, and a routine Netgear firmware update can silently wipe it out since it lives outside the NAS's own app framework. Not worth the ongoing maintenance risk for a home NAS.

The Subnet Router Idea

Tailscale has a built-in answer for exactly this situation — a device that can't run the Tailscale client itself: a subnet router. It's a real Tailscale peer that also happens to sit on the same local network as the un-installable device, and volunteers to forward traffic for that network's whole address range to every other device on the tailnet.

The natural candidate was the Alienware Ubuntu server — it was already a Tailscale peer, it was already living on the home LAN right next to the NAS, and it's always powered on.

What This Plan Deliberately Avoids

Port forwarding was never on the table. Forwarding the NAS's SMB port (445) through the router would expose file sharing directly to the public internet — a well-known, heavily targeted attack surface. A Tailscale subnet router achieves the same goal (remote access) through a private, encrypted mesh instead, with nothing ever exposed publicly.

Build Log

What actually happened, in the order it happened — including the parts that didn't work the first time.

Setting Up the NAS Itself

The NAS's admin page was found via the router's connected-devices list rather than RAIDar (see Early Dead Ends). Its two secondhand 2TB Samsung HDDs (age unknown, roughly 5–10 years old) were configured as X-RAID — ReadyNAS's auto-managed RAID mode, which behaves as a RAID1 mirror with two equal-size drives — giving about 1.81TB of usable, mirrored storage. The device itself was renamed from its factory name to cbm-nas-01.

Common Pitfall

RAID1/X-RAID protects against one drive failing — it is not a backup. It does nothing against accidental deletion, ransomware, or both drives failing at once. Given the drives' unknown age, a real off-NAS backup plan is a flagged TODO, not yet built.

Creating a Personal User Account and Shares

A non-admin clayton account was created for everyday use — admin is reserved strictly for NAS configuration and is never used for regular file access, on any device. Shares created: media-library (with movies/tv/other subfolders, feeding Plex — which reads it directly on the NAS itself, so no network credentials are needed for Plex specifically), a general-purpose vault share, and clayton-docs, a personal folder restricted to just admin and clayton.

Tip

Only the SMB protocol was enabled on these shares. For a Windows-first household, NFS (Linux/Unix), AFP (legacy Mac), FTP, RSYNC, and HTTP/WebDAV are all unnecessary unless a specific need for one comes up later. DLNA is worth keeping only on shares that actually stream media to smart TVs or similar devices.

Mapping Drives From Windows

The very first attempt to map \\cbm-nas-01\media-library failed with a generic "extended error." The cause: Windows had tried to connect anonymously (no credentials supplied), and modern Windows blocks insecure guest SMB logons by default. Checking "Connect using different credentials" and supplying the real NAS login fixed it.

Cleaning Up Tailscale Nodes

In the Tailscale admin console: the dead duplicate node was deleted, and the real working node was renamed — first from cbm-alienware-ubuntu-1 to cbm-alienware-ubuntu, then again to the clearer, final name cbm-home-server-01.

Turning the Home Server Into a Subnet Router

On the Ubuntu box itself, four things had to happen, in order:

# 1. Confirm the home LAN subnet
ip -4 addr show
#   -> found: 192.168.1.128/24, so the subnet is 192.168.1.0/24

# 2. Enable IP forwarding, persistently (survives reboots)
echo 'net.ipv4.ip_forward = 1' | sudo tee -a /etc/sysctl.d/99-tailscale.conf
echo 'net.ipv6.conf.all.forwarding = 1' | sudo tee -a /etc/sysctl.d/99-tailscale.conf
sudo sysctl -p /etc/sysctl.d/99-tailscale.conf

# 3. Advertise the route to the tailnet
sudo tailscale set --advertise-routes=192.168.1.0/24

Step 4 happened back in the Tailscale admin console: opening cbm-home-server-01's Edit route settings panel and approving the advertised 192.168.1.0/24 route. While there, key expiry was also disabled on that machine — since it's now a permanent server role, an expired auth key (Tailscale's default is periodic re-authentication) would have silently broken remote NAS access at some point in the future until someone happened to notice.

Reserving the NAS IP Address

On the router (an AT&T fiber gateway, model BGW320-500), the first page tried — Firewall › NAT/Gaming — turned out to be the wrong tool entirely: that's port forwarding, exactly what this whole plan was built to avoid. The correct page was Home Network › Subnets & DHCP › IP Allocation. The NAS was found in the device list (still showing its old factory name, nas-77-BC-78 — cosmetic, harmless) and given a fixed/reserved DHCP address: 192.168.1.132.

Common Pitfall

The router's fixed-address list is just a pool of available addresses — it doesn't automatically warn you if one is already claimed by another device. 192.168.1.69 was skipped specifically because it was already the laptop's (cbm-slim7i) address; reusing it would have caused an IP conflict between two devices.

The Anonymous Access Trap

With everything above in place, mapping the brand-new clayton-docs share still failed — first "Access is denied," then a stranger error: "Multiple connections to a server or shared resource by the same user, using more than one user name, are not allowed."

The cause: Windows only allows one set of credentials per remote server at a time. Because media-library, Music, Pictures, and Videos still had "Allow anonymous access" turned on, simply browsing the NAS in File Explorer silently opened an anonymous session in the background — which then blocked the explicit clayton login attempt to a different share on that same server.

Fix, in two parts:

# Clear the stuck session
net use * /delete /y

...and then, permanently: "Allow anonymous access" was unchecked on every remaining share. Once no share offers an anonymous fallback, every connection to the NAS — regardless of which share — consistently requires the real login, so this conflict can't recur.

Verifying Remote Access For Real

The first "remote" test wasn't actually valid — it was run while still connected to home Wi-Fi, which only proves local LAN access still works, not the Tailscale path. The real test required getting a device fully off the home network: an iPhone switched to cellular data (with Tailscale showing "Connected"), and separately, the laptop tethered to that same iPhone's personal hotspot.

Both succeeded — reaching \\192.168.1.132\clayton-docs exactly as if on the home LAN, and proven bidirectionally: a file created from the hotspot-connected laptop appeared instantly in the NAS admin's own file browser.

Where Things Stand Now

End to end, the whole path works: any of your Tailscale-connected devices can reach the NAS's shares from anywhere, using a real login, with nothing exposed to the public internet.

Connecting to clayton-docs Going Forward

Day-to-day, this is all that's needed on each platform — no more troubleshooting required, assuming Tailscale shows "Connected" when off the home network.

From Windows

File Explorer:

  1. This PC › Map network drive
  2. Folder: \\192.168.1.132\clayton-docs
  3. Check Connect using different credentials
  4. Username clayton, then your NAS password

Or from a terminal:

net use Z: \\192.168.1.132\clayton-docs /user:clayton * /persistent:yes

The * makes it prompt for the password securely instead of storing it in plain text in your shell history.

From Linux

GNOME Files (Nautilus):

  1. Files › Other Locations › Connect to Server
  2. Enter smb://192.168.1.132/clayton-docs
  3. Choose Registered User, enter clayton and your password

Or mount it directly:

sudo mkdir -p /mnt/clayton-docs
sudo mount -t cifs //192.168.1.132/clayton-docs /mnt/clayton-docs \
  -o username=clayton,uid=$(id -u),gid=$(id -g)
Tip

For a permanent mount via /etc/fstab, use a separate credentials file (chmod 600) rather than putting the password directly in fstab, which any local user can read.

From iPhone or iPad

  1. Open the Files app › Browse
  2. Tap “…” (top-right) › Connect to Server
  3. Enter smb://192.168.1.132/clayton-docs
  4. Choose Registered User, enter clayton and your password

Once connected, it's saved under Shared in the Files sidebar for next time.

Glossary

TermDefinition
Anonymous / Guest SMB AccessA share setting that lets anyone connect without a username or password. Convenient, but on Windows it can cause session conflicts with named logins to the same server (see The Anonymous Access Trap), and it's a real security gap on any network you don't fully trust.
DHCPDynamic Host Configuration Protocol — the router's built-in service that automatically hands out IP addresses to devices when they join the network, so nobody has to configure one by hand.
DHCP ReservationA rule telling the router "always give this specific device the same IP address," identified by its MAC address. Prevents a device's address from silently changing later.
DLNAA media-streaming standard (separate from file sharing) that lets devices like smart TVs browse and play media directly from the NAS. Has its own "friendly name," independent of the NAS's real hostname — a common source of confusion.
IP ForwardingA router-like behavior where a device passes along network traffic that isn't addressed to itself. Off by default on a Linux machine; had to be explicitly enabled for the home server to act as a subnet router.
MagicDNSA Tailscale feature that lets devices on the tailnet reach each other by name instead of by IP. Doesn't apply to the NAS here, since the NAS isn't itself a Tailscale device — only its LAN IP works remotely.
Mesh VPNA VPN model where every device connects directly to every other device (rather than all traffic funneling through one central server). Tailscale is a mesh VPN built on WireGuard.
NASNetwork-Attached Storage — a dedicated device whose job is to store files and serve them to other devices over the network, as opposed to a general-purpose computer.
Port ForwardingA router rule that exposes a specific device/service directly to the public internet. Deliberately avoided in this project in favor of Tailscale — see The Subnet Router Idea.
RAID1 / X-RAIDA storage mode that mirrors data across two drives, so the NAS survives one drive failing. X-RAID is Netgear's auto-managed version of this. Important: not a substitute for a real backup.
SMBServer Message Block — the standard Windows file-sharing protocol, also supported by macOS, Linux, and iOS. What every "network drive" connection in this guide runs on.
SubnetA block of IP addresses that can reach each other directly without going through a router — e.g. every device numbered 192.168.1.1–192.168.1.254. Your home LAN is one subnet.
Subnet Router (Tailscale term)A Tailscale peer that advertises "route traffic for this whole address range through me," giving the rest of the tailnet access to devices on its LAN that can't run Tailscale themselves — exactly the role cbm-home-server-01 plays for the NAS.
TailnetTailscale's term for your own private network of devices — everything connected under one Tailscale account.
UNC PathThe \\servername\sharename format Windows uses to address a specific network share directly — the thing typed into "Map network drive" or a browser/Explorer address bar.
VPNVirtual Private Network — broadly, any technology that creates a private, encrypted connection across a public or untrusted network.
WireGuardA modern, lightweight VPN protocol known for being fast and simple to reason about. Tailscale is built on top of it.
