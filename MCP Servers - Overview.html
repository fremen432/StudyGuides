What Is MCP?

The Model Context Protocol (MCP) is an open specification, originally published by Anthropic, that standardizes how AI applications connect to external tools, data sources, and systems. Instead of every AI app writing its own custom integration code for every tool it wants to use, MCP defines one common interface: build a server once, and any MCP-compatible client — Claude Desktop, Claude Code, or another vendor's app — can talk to it.

Tip

MCP isn't an Anthropic-only thing despite where it started — it's a published, versioned specification, and other AI vendors and client apps have adopted it too. Think of it more like a network protocol than a proprietary feature.

Why It Exists

Before a shared protocol, connecting M AI applications to N tools meant something close to M×N custom integrations — every app maintaining its own bespoke code for GitHub, Slack, a database, a filesystem, and so on. MCP turns that into M + N: an app implements the client side once, a tool builder implements the server side once, and any client can reach any server.

Core Building Blocks

Every MCP server exposes its capabilities through up to three primitives. A server doesn't need to implement all three — a simple one might offer just tools.

Tools

Functions the model can actively call, usually with side effects — create a file, run a query, send a message. The model decides when to call a tool and with what arguments; the server executes it and returns a result.

Resources

Read-only data the client can fetch and hand to the model as context — a file's contents, a database schema, a log excerpt. Resources are for reading, not acting.

Prompts

Reusable, server-defined prompt templates — often parameterized — that a client can surface to the user as a shortcut for a common task (e.g. "summarize this PR" with a PR-number argument).

Common Pitfall

Tool descriptions are part of the prompt the model sees — a vague or misleading description leads to the model calling the wrong tool, or the right tool with wrong arguments, just as easily as bad prose confuses a human reader.

Transports — How Client and Server Talk

MCP defines the message format (JSON-RPC 2.0), but a server can be reached over more than one underlying transport depending on where it runs.

stdio (Local Processes)

The client launches the server as a local subprocess and exchanges JSON-RPC messages over its standard input/output streams. No network involved — this is the default for a server that runs on the same machine as the host app (most desktop MCP servers work this way).

HTTP + Streamable HTTP (Remote Servers)

For a server that isn't local — running on another machine, or as a hosted service — the client connects over HTTP, with the server able to stream multiple messages back (originally via Server-Sent Events, more recently via the newer "Streamable HTTP" transport). This is what makes a remote, shared, or multi-tenant MCP server possible.

Building a Simple MCP Server

Choosing an SDK

Official SDKs exist for several languages — Python and TypeScript are the most mature, with community and vendor-maintained SDKs for others (Java, Kotlin, C#, Go, Rust). Pick whichever matches the tool you're wrapping; a server that shells out to an existing CLI is often the fastest path to something useful.

Anatomy of a Tool Definition

At minimum, a tool needs a name, a description the model will read, a JSON Schema for its arguments, and a handler function:

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("example-server")

@mcp.tool()
def get_weather(city: str) -> str:
    """Return the current weather for a given city."""
    return fetch_weather(city)

mcp.run()
Tip

The docstring/description isn't just documentation — it's what the model reads to decide whether and how to call the tool. Write it the way you'd explain the function to a new teammate, not the way you'd write an internal code comment.

Connecting Clients to Servers

Claude Desktop / Claude Code Config

Most desktop MCP clients register a server with a small JSON config entry — a command to launch it (for stdio) or a URL (for HTTP):

{
  "mcpServers": {
    "example-server": {
      "command": "python",
      "args": ["path/to/server.py"]
    }
  }
}

Other MCP Clients

The client ecosystem has grown well past Anthropic's own apps — various IDEs, agent frameworks, and third-party AI assistants can act as MCP hosts. A server built to spec doesn't need to know or care which client is talking to it.

Security & Permissions

Why Permission Prompts Exist

A tool call can do real things — write a file, send an email, run a query against production data. Clients typically gate a new or sensitive tool behind a one-time or per-session permission prompt precisely because the model is deciding to invoke it, not a human clicking a button.

Common Risks

An MCP server is code you're choosing to run — treat a random community server with the same scrutiny as any other third-party dependency before pointing it at anything sensitive.

Common Pitfall

Prompt injection via tool output. A tool's return value — the contents of a fetched webpage, a file, an API response — becomes part of what the model reads next. A malicious or compromised data source can embed instructions in that content aimed at the model, not the user. Treat tool output as data, and be wary of servers that fetch content from untrusted sources.

Scoping and least privilege

Where a server supports it, grant the narrowest scope that does the job — a filesystem server pointed at one project folder rather than the whole drive, a database credential with read-only access if the task never needs to write. The same principle you'd apply to any API key applies here.

Real-World Examples & Ecosystem

Well-Known Servers

A wide range of servers already exist for common systems — filesystem access, GitHub, Slack, Google Drive, Postgres and other databases, browser automation, and many SaaS products. Most popular developer tools now have an MCP server maintained either by the vendor or the community.

Where to Find More

Anthropic maintains a public repository of reference servers, and a growing number of community registries index third-party servers by category. As with any dependency, prefer a server that's actively maintained and, ideally, open source you can actually read before pointing it at something sensitive.
